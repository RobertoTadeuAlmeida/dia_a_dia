## Responsabilidades do AuthRepository
O `AuthRepository` deve ser responsável **apenas** por:
- Autenticação via e-mail e senha usando Supabase
- Autenticação social via Google OAuth2 usando Supabase
- Persistência e remoção da sessão autenticada usando `flutter_secure_storage`
- Recuperação da sessão persistida ao iniciar o app
- Logout e limpeza dos dados de autenticação local

---

## Métodos obrigatórios

```dart
Future<void> signInWithEmailAndPassword(String email, String password)
Future<void> signInWithGoogle()
Future<void> signOut()
Future<bool> hasValidSession()
Future<void> restoreSession()
```

## Regras de implementação

### Supabase
- Usar `SupabaseClient` injetado via construtor
- Não instanciar `Supabase` diretamente dentro do repository
- Supabase ainda não está configurado no projeto — criar o código preparado para integração futura
- Marcar os pontos de integração com comentário: `// TODO: Supabase integration`

### flutter_secure_storage
- Usar `FlutterSecureStorage` injetado via construtor
- Chave de armazenamento da sessão: `'auth_session'`
- Armazenar apenas o token de sessão — nenhum dado sensível extra

### Tratamento de erros
- Capturar exceções do Supabase e relançar como `Exception` com mensagens em português:
    - Credenciais inválidas → `Exception('E-mail ou senha inválidos.')`
    - Cancelamento do Google → `Exception('autenticacao_cancelada')` — usar essa string exata para o ViewModel identificar o cancelamento sem exibir erro
    - Sem conexão → `Exception('Sem conexão com a internet.')`
    - Erro genérico → `Exception('Ops! Não foi possível acessar a aplicação. Tente novamente mais tarde.')`
- O repository **não deve** controlar estado de tela nem exibir mensagens — apenas lançar exceções

### O que NÃO implementar
- Validação de campos (responsabilidade do ViewModel)
- Lógica de redirecionamento de rotas
- Estado de loading
- Qualquer lógica de UI
